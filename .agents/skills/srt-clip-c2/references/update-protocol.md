# C2 Universal｜固定版本更新协议 (Update Protocol)

> 治理级规则。适用于今后每次业务规则、类目模块、平台适配、长文本、性能、合规基线及发布流程的变更。执行优先级：AI-First Constitution > 本更新协议 > 具体业务模块。不得以本协议替代或降低 SKILL.md 的现有剪辑要求。

## 一、更新的六项固定审查

1. **AI 主导**：先写出不依赖 Python、脚本、API、联网或中间 JSON，且原始文本可靠可读时 AI 能独立执行的主路径。商品归属、亮点、语义去重、结构、合规语境与最终取舍仍归 AI。
2. **工具最小化**：新增工具须明确机械用途、触发条件、准确性或端到端效率的可验证收益。禁止将工具可用性、环境自检或多层 Gate 设为普通文本任务前置条件；不得为实现形式上的自动化而增加重复调用。
3. **环境零强制与自动降级**：说明工具不可用时的 AI 主路径、需要告知用户的核验边界，以及仅在输入本身缺失、不可恢复的截断、关键来源无法确认等情况下暂停受影响部分；不能伪称运行过程序。
4. **质量不退步**：逐项核对原话真实性、字幕编号与来源、商品归属、独立购买信息覆盖、按新增信息去重、合规语境、1.2 倍速 120 秒硬上限和固定五部分输出。主题或类别不得成为删除理由；不得为了覆盖率新增普通任务的台账、遗漏扫描、全文复查或模型轮次。
5. **更新验收**：对受影响路径做最小充分回归；覆盖常规文本、相关长文本/多商品/多方案和对应类目场景。开发期可按需使用测试脚本；不得让发行测试成为日常执行的硬依赖。未实际测试的项目标记“未验证”。
6. **发布与同步**：记录实际变更的文件、版本号、GitHub/插件/便携包/云盘各渠道状态；仅对实际上传且可核实的渠道声明“已同步”。对比端到端耗时与工具调用次数时，只能报告实测，不得凭推测断言“更快”。

## 二、三条一票否决

- **无明确收益的工具否决**：新增日常工具调用，却无法说明其明确、可核实的准确性或端到端效率收益，不得发布。
- **质量下降否决**：简化步骤导致原话被改、商品串用、不同关键卖点漏选、来源编号错误、时长计算不可靠或合规误判，不得发布。
- **新环境硬依赖否决**：本来 AI 可以仅凭可靠文本完成的普通任务，新版本要求先装 Python、安装依赖、联网、生成 JSON 中间件或通过环境测试才能开始，不得发布。

上述条款不得用于禁止必要的可选机械校验：复杂长文本或时长计算可按需调用工具；其结果不能替 AI 作语义决策。

## 三、每次更新的固定记录格式

- **基准与目标版本**：旧版本 → 新版本；改动性质（业务/类目/平台/效率/治理/修复）。
- **变更范围**：具体文件、变更理由、影响场景和明确不变的规则。
- **AI 独立主路径**：在可靠文本可读且无工具时如何完成核心任务。
- **工具决策与降级**：每项工具的用途、触发条件、增益证据、不可用处理。
- **质量与兼容检查**：原话、商品归属、卖点覆盖、时长、固定五部分及相关类目/长文本检查结果。
- **端到端效率**：实测数据和条件；没测则写“未测”，不得以减少步骤数冒充耗时提升。
- **发布状态**：GitHub / 私人插件 / 便携包 / 云盘 / 其他平台逐项写“已核实 / 未同步 / 待核实”，不得笼统宣称全部完成。
- **最终判定**：“通过 / 不通过 / 待验证”，三项一票否决逐项写明。

## 四、执行边界

本协议只约束未来版本的**开发与发布**，不增加每次使用“srt文案”时的分析步骤、固定表单、Python 调用、环境检查或额外对用户展示的字段；日常五部分交付保持不变。

版本升级完成后，只有通过核验的已发布渠道才可称为“当前已更新版本”；其他渠道必须明确保留旧版状态。
