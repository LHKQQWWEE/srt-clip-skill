# C2 Universal｜永久增量更新治理规则

本协议是 C2 Universal 后续所有 Skill 修改、维护、测试和发布任务的默认治理标准。用户已确认的修改要求直接执行，不重新制定方案；本协议只约束开发维护，不增加日常 SRT 运行步骤、强制读取或用户交互。

## 1. 更新等级自动识别

AI 按实际影响范围自主判断等级，无须询问用户。影响扩大时自动提高检查范围，不得为了提速忽略风险。

### L1：局部更新

适用于单项规则、展示格式、正式词库增删、单点缺陷修复。只修改目标规则源，运行该项相关测试并自动同步其派生文件；不审计无关模块。

### L2：模块级更新

适用于开头机制、正文动态排序、上下文连续性、商品识别等独立功能模块。修改受影响模块，检查直接关联规则，运行专项测试及直接、间接受影响的回归；无关模块不做重复人工审查或无关重构。

### L3：架构级更新

适用于核心业务架构、主执行流程、工具依赖、跨模块重大变更。执行必要的架构审查和完整回归。若 L1 或 L2 修改实际影响扩大到此范围，自动升为 L3。

## 2. 唯一有效版本基准

每次修改前确认实际生效 Skill 与原插件的版本、当前 release ID、唯一运行入口、GitHub 目标分支最新提交，以及现有交付包版本。用版本信息、Git 提交和受影响文件哈希核对来源；只对不一致或受影响文件执行必要差异检查。

实际生效版本是修改起点。不得用旧 ZIP 覆盖较新的 Skill、插件或 GitHub 源码；发现多个来源不一致、来源不明或哈希异常时，先确认差异及其影响，再合并仍然有效的变化并扩大核查。版本和受影响文件一致时，不重审未变更的业务规则。

## 3. 最小必要修改

1. 只修改本次受影响的权威规则和必要关联条款。
2. 保持未受影响的业务规则、知识包、正式词库、商品事实边界和交付格式不变。
3. 不做无关重构、无关优化或大范围重写。
4. 发现异常时定位具体根因并局部修复；不因局部异常重跑全部升级流程。

## 4. 唯一权威源、派生文件与轻量依赖映射

同一规则只保留一个权威维护来源。禁止手工在多个相同正文中重复改写；派生正文、摘要、镜像和便携版通过构建或同步程序生成。只补足现有工具确实不能完成的必要能力，不创建庞大维护系统或重复映射文档。

| 变更源 | 必要派生与关联检查 |
| --- | --- |
| references/editorial-policy.md、references/final-check.md | scripts/build_runtime.py 生成 runtime-current.md 与 runtime-manifest.json；刷新 execution-summary.json；由 scripts/build_portable.py 重建 C2-Universal-Portable.md；同步 .agents 镜像并验证相关规则测试 |
| references/update-protocol.md | 同步到 .agents 镜像并纳入 Skill ZIP 与插件发行包；不得编译进日常 runtime 或便携运行正文 |
| VERSION、SKILL.md、plugin.json、.codex-plugin/plugin.json | 运行正文、manifest、摘要、便携版、镜像、Skill ZIP 和现有插件发行包；核对版本标记和唯一入口 |
| scripts、tests、发布验收记录 | 只运行相关构建/测试；同步镜像并纳入 Skill ZIP；开发脚本不得进入日常运行正文 |

当前 Skill 的 .agents/skills/srt-clip-c2 是 skills/srt-clip-c2 的派生镜像，使用 scripts/sync_skill_mirror.py 同步，禁止手工分别维护两份相同规则。发布前按文件哈希和必要差异检查确认镜像、生成正文及版本一致。

## 5. 精准测试与局部修复

1. 实际测试本次修改功能，并对直接、间接受影响的规则做关联回归。
2. 在正式发布前集中运行自动构建和快速回归；不对未受影响模块重复进行人工语义审查。
3. 测试失败时定位具体原因，局部修复并复测；不因一个局部异常反复执行整个升级流程。
4. 不得把未实际测试的结果标记为通过。测试范围不足时补充最少必要样本，并明确区分真实素材与测试样本。
5. 原话真实性、商品归属、合规、有效信息覆盖、原始序号准确性、独立成片和固定五部分交付等红线不得降低。

## 6. 全量发布门禁与历史清理

影响跨文件或涉及已发现旧规则时，扫描全部权威源、入口、运行文件、摘要、便携版、测试、脚本、插件目录和 GitHub 目标分支；不得把初始发现清单当作扫描上限。逐条做语义一致性审计，不只搜索同义词或替换关键词。门禁必须覆盖：

1. 新旧规则语义冲突及废弃规则的改写、换序、否定包装或其他语义变体。
2. 旧验收报告、废弃测试、历史版本说明、重复规则、历史压缩包或其他可被误读的历史材料是否混入正式 Skill/插件包或当前源码目录。
3. 权威源与运行正文、执行摘要、manifest、便携版、入口提示及双目录镜像的一致性；派生文件只能在权威源修正后由构建/同步程序生成。
4. 当前测试断言是否验证现行规则；不得保留已废弃语义的正向断言、测试说明或夹具。
5. Core、Skill、Plugin 版本，manifest 源文件清单和哈希、运行正文哈希、摘要绑定哈希、ZIP 文件集合与内容哈希的一致性。

任何门禁失败、存在无法解释的冲突或读回不一致，均禁止发布。历史追溯只依赖 Git 提交历史；正式运行包、插件发行包和当前有效源码目录不分发已废弃业务规则或旧版历史资料。只删除已经废弃的资料，不删仍服务于当前规则的测试。

门禁由开发期 `scripts/release_gate.py` 与当前测试体系执行；仅用于更新、构建、测试和发布，不加入日常 Skill 入口、强制读取链、Token 消耗或工具依赖。

全部修改、门禁和关联回归通过后集中发布一次：更新版本；向 GitHub 目标分支提交同一变更集；原位更新现有插件并保留插件 ID、权限和唯一入口；同步实际生效 Skill、.agents 镜像、便携版、运行正文、执行摘要、manifest、当前测试及独立 Skill ZIP；逐渠道读回验证版本、文件集合与哈希。不得重复创建插件或反复发布未验收版本。无法完成的渠道如实标为未同步或未验证。

最终交付报告只说明实际修改、测试结果、同步状态和未解决限制；未验证事项不得表述为成功。

## 7. 开发维护与日常运行隔离

本协议仅在开发、维护、测试和发布阶段使用。它不进入日常 SRT 强制读取链、runtime-current.md 或 C2-Universal-Portable.md；不得增加日常 Python、脚本、CLI、外部工具调用、AI 推理轮次或规则读取负担。开发维护允许使用 Python 和自动化工具。

## 8. 后续默认执行流程

以后任何 Skill 修改请求默认按以下顺序完成，无须用户重复指定增量更新、精准测试、同步或旧规则清理：

确认实际有效版本与唯一入口 → 自动判断 L1/L2/L3 → 定位受影响规则及依赖 → 最小必要修改 → 自动构建与精准测试 → 对异常局部修复并复测 → 定向清理旧规则 → 一次性同步、发布、读回验证并交付。

## 9. 持续有效的业务边界

更新治理不得改写或削弱已确认的业务规则，包括：多商品先选商品再选开头；展示所有达到质量门槛且实质不同的开头候选，不设候选数量上限并使用固定四项格式；用户最多选择三个，用户选择几个开头就分别生成几条独立成片，每条必须以对应所选开头开始；日常运行零 Python 依赖；原话、序号与商品归属硬核对；每条正文独立动态排序与重组，并逐条覆盖有效卖点；固定五部分成交交付；现有时长与超长例外；适用原文促单、合规与上下文连续性边界。每次升级只在明确范围内修改，其他规则继续有效。

第一阶段验收完成前，第二阶段的整条内容板块化编排不属于当前运行规则，也不得提前合并进本次 Skill。
