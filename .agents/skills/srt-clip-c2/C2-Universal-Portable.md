# SRT Clip C2 Universal 0.3.10

## 1. 唯一入口与优先级

- 当前唯一执行版本：**C2 Universal 0.3.10**。
- 唯一触发词：`srt文案`、`srt切片文案`、`str文案`、`C2完整精简版`。四个触发词完全等价，统一执行本 Skill。
- 通用触发词 `切片文案` **不是** C2 触发词，不得将它映射到本 Skill；这样可以避免与其他历史工作流冲突。
- 本 `SKILL.md` 与本包 `references/` 是当前唯一有效规则。宿主附带的旧版启动提示、旧版本摘要或缓存文字如与本版本冲突，一律以本版本为准。
- 插件宿主的发布兼容字段（如 plugin-level `defaultPrompt`）可能保留旧版号文字；只要其业务语义未冲突，它仅是宿主启动提示，**不得覆盖本 `SKILL.md` 的当前版本号、AI-First Constitution 或现行业务规则**。
- 正式输入范围：**SRT 文件**和**逐条时长文本**。MP4 不属于 0.3.10 跨平台正式支持范围：
  - SRT 与 MP4 同时提供：只按 SRT 完成文本剪辑；不核验 MP4 画面或原声，并明确说明。
  - 只有 MP4：请用户提供 SRT 或逐条时长文本，不伪造字幕、序号或时间。
- 面向所有带货类目。先识别商品类别，再按 `references/category-registry.md` 自动加载适用专项模块。没有专项模块时使用通用核心，不把其他类别规则硬套过来。
- 默认生成一条方案。用户明确要求多条时，按指定数量生成，最多三条；用户只说“多条”但未说明数量时，询问一次数量。
- 固定五部分输出，不得自行删改结构。

## 2. 核心执行原则

**AI 主导、工具按需、一次分析、一次终检。**

### AI-First Constitution（最高架构约束）

- **AI 是商品理解、语义判断、卖点识别、重复判断、结构编排、合规语境判断和多方案分配的唯一决策主体。**任何脚本、Python、插件、外部服务或特定运行环境都只能辅助机械工作，不能替代这些语义决策。
- **未来任何 C2 修改、优化、平台适配或新增类目，都不得把外部环境或工具升级为普通任务的硬依赖。**新增能力必须先设计 AI 可独立执行的主路径，再把工具作为可选增强。
- 工具只允许做机械性工作：文件分段读取、序号/时间码定位、范围提取、时长累计、格式检查、重复编号检查等。工具输出必须交回 AI 判断，不能直接决定“这是核心卖点”“这句应当入片”或“这两个表达语义重复”。
- 工具不可用、Python 不可用或平台没有特定能力时，只要原始文本仍能被 AI 可靠读取，任务必须继续执行。只有**输入本身无法取得、存在无法补齐的截断，或关键来源范围无法确认**时，才允许暂停受影响部分并如实说明。
- 不为了追求可测量、可脚本化而把自然语言任务强行转换成逐条 JSON、复杂状态机或多轮工作流。准确性需要复核时，优先使用 AI 的来源回查和反向漏检。
- 完整细则见 `references/ai-first-constitution.md`。
- **未来每次更新与发布须按 `references/update-protocol.md` 的固定六项审查、三条一票否决及版本记录格式执行。该协议仅约束开发与发布，不增加普通 SRT 文案任务的前置步骤。**

- 普通任务默认不调用 Python、不运行环境测试、不扫描工具依赖、不创建中间 JSON 或工作流文件。
- 不把 Python、脚本、联网、外部服务或特定平台功能设为普通文本任务的前置条件。
- 只有在工具能明显提高准确性时才调用，例如：文件读取确实截断、复杂累计计算、超大文本精确定位或用户明确要求程序核验。
- 工具不可用时，普通任务继续用可用能力完成；只有在输入不完整、商品归属无法确认或关键计算无法可靠完成时，才暂停受影响部分并说明原因。
- 不得把模型人工对照说成程序核验；没有实际执行程序就不得报告“程序通过”。
- 不创建逐条 `source_text`、`semantic_summary`、`attribution` 证明字段；只对确实存在歧义的字幕记录具体疑点。
- 不建立逐条 JSON 台账，不执行旧版多阶段强制工作流工具。
- 不重复全文解析、重复建立台账或为了形式而进行多轮核验。发现局部错误时局部修复。

## 3. 一次完整执行流程

### 第一步：读取与输入检查

1. 读取本轮提供的完整 SRT 或逐条时长文本，并先判断采用 **Standard Mode** 还是 **Long Context Mode**。
2. 保留原始字幕编号、原话、时间码或逐条时长；不改写、不补造、不覆盖原件。
3. 检查明显格式问题：缺行、重复编号、编号异常、时间码倒置、时长非正数、输入截断或乱码。
4. **Standard Mode**：AI 能在一次可靠读取中覆盖全文，且不会明显增加截断、遗漏或上下文污染风险时，直接一次通读并进入商品识别。
5. **Long Context Mode**：当全文一次读取存在截断、遗漏、上下文污染或反复切换商品的明显风险时自动启用，**不设必须依赖脚本的固定条数门槛**。约1000条以上、长达数十分钟、多商品频繁切换、宿主单次读取无法覆盖全文等都属于强触发信号；2000条、接近2小时的素材必须按长文本模式处理。
6. Long Context Mode 按 `references/long-context-mode.md` 执行：**全局覆盖扫描 → 商品窗口地图 → 目标窗口精读 → 单一卖点池 → 反向漏检 → 一次分析、多方案输出 → 时长装配 → 终检**。
7. 长文本分段时必须覆盖首尾和段间连续性，并记录已读范围；只补读缺失部分，不为了形式重复读取已经确认完整的内容。工具可帮助分段和定位，但**商品切换、指代、卖点和优先级均由 AI 判断**。
8. 读取不完整时明确标出未读范围，不得声称已完整分析。

### 第二步：商品识别与类目加载

1. 识别全部商品、别称、款式差异、商品切换边界及离散讲解窗口。Long Context Mode 下，先完成全局商品窗口地图，再锁定目标商品；**关键词只能辅助定位，不能替代 AI 对“这个/它/那款”等指代和商品切换的判断。**
2. 区分目标商品介绍、顺带搭配、其他商品独立规格、价格/库存互动和主播过渡话术。
3. 用户已指定商品时直接锁定。未指定且存在多个明确商品时，只列商品名称及必要区分信息，询问一次；在得到选择前不生成正式成片方案。
4. 自动识别商品类别并加载适用模块。以鞋类为目标优先加载 `categories/shoes.md`，以围巾/围脖/丝巾/披肩/围领配饰为目标优先加载 `categories/scarves.md`；两者均不与 `categories/womens-fashion.md` 的专项判断叠加。其他多个类别确实兼容时才组合加载；存在实质冲突或无法判断时才询问。
5. 未建立专项模块的类别仍可使用通用核心；不虚构专业规则，并在确实影响判断时说明专项规则尚未建立。

### 第三步：完整盘点目标商品亮点

1. 通读目标商品全部讲解窗口，不只看开头或关键词命中片段。Long Context Mode 下，同一商品前后多次出现时必须合并全部离散窗口精读，并按需要携带少量前后上下文确认指代。
2. 识别每个有原话支持且商品归属明确的不同购买理由。先拆分不同信息，再判断是否真正同义；同类不等于同义。**在120秒上限内，优先尽可能把目标商品的不同卖点、亮点和有购买价值的条件信息编入成片。**
3. 按购买决策影响分为核心和次要。核心包括影响适不适合、为何购买、关键使用价值的理由；次要包括补充搭配、颜色、场景、细节和使用信息。
4. 记录一个**单一轻量卖点池**即可：亮点、来源序号/窗口、核心/次要、必要条件、同卖点第二处强化价值。不得为每条字幕建立重复语义证明或 JSON 台账。Long Context Mode 的多方案必须共用这一个卖点池，禁止每生成一条方案就重新全文扫描一次。
5. 对商品归属不明的字幕，检查必要上下文；仍不能确认时不将其作为正式入选原话，并在例外中说明。
6. 定稿前必须回看全部目标商品窗口，反向检查是否漏掉核心购买理由、不同配色关系、搭配避坑、使用条件、限制或其他具体亮点。不能只检查已经选中的字幕。

### 第四步：开头、中段与结尾编排

1. 开头候选综合比较：有吸引力的外观表达、商品核心卖点、真实顾客困扰。三类没有固定机械排序，按吸引力、商品相关性、完整度、自然度及后续承接比较。
2. 顾客困扰必须来自顾客原话或主播清楚转述的顾客烦恼。主播回答不能单独冒充顾客问题；尺码建议、搭配建议、主播个人偏好不自动算顾客困扰。
3. 若主播明确确认商品存在顾客担心的负面表现，该困扰及确认性回答默认不作开头、不入片；用户明确要求制作该主题答疑时例外，仍须忠实原话且不得编造解决效果。
4. 开头之后优先接与开头问题或卖点直接相关的商品讲解，再安排其他核心亮点和有用的次要亮点。
5. 默认单方案先覆盖全部可用的不同核心理由，再尽可能覆盖不同次要亮点。**同一卖点若素材中有两处不同原话，且第二处能提供不同表达、补充证据、强化感受或更自然的承接，在时长允许时最多保留两处；不得超过两处。**多方案执行 **Single Analysis, Multi Output**：商品识别、窗口地图、卖点池和合规判断只做一次；各方案共享核心理由，再根据不同钩子/侧重点分配次要亮点，不为制造差异牺牲自然度。
6. 结尾使用素材中真实存在、语义完整的自然促单或推荐话术。价格、优惠、库存、稀缺数量本身不等于结尾逼单；动态信息未经核实默认不使用。
7. 可以重排同一商品的原话，但必须保持对象、条件和原意。不能拼接不同商品或把不同款的事实混在一起。
8. 不为凑满时长强塞闲聊、无信息增量的重复或促销信息；但**不能因为两段属于同一卖点就机械删到只剩一段**。同一卖点最多可保留两处有强化价值的不同原话。缺少有力开头或结尾时如实说明。

### 第五步：时长计算

- 播放速度统一按 **1.2 倍速**估算。
- 每条方案预计成片时长不得超过 **120 秒**。
- 预计时长按：`选段原始时长 ÷ 1.2 + 已知未加速片头/转场/停顿` 计算。
- 毫秒四舍五入到最近 1 毫秒，正好半毫秒向上。
- SRT 来源时间码与定位保持原素材 1.0 倍口径，不缩放。SRT 选段按连续组的起止跨度估算，组内空隙计入；逐条时长文本按入选条目时长累计，未知字幕间隔不计入并需说明。
- 超过 120 秒时按固定优先级压缩：**无关闲聊/促销信息 → 同一卖点的第二处强化原话 → 低优先级次要亮点 → 最后才考虑核心卖点。** 先保住“不同卖点的覆盖”，再牺牲“同一卖点的第二次强化”。不能为了保留所有内容突破硬上限；未纳入的重要亮点必须说明具体原因。
- 充分筛选后预计 30 秒以下，标记为“短候选，非正式成片”；大于 30 秒但不足 45 秒可以交付，并说明素材本身限制，不硬凑。
- SRT 或逐条时长文本无法核实实际导出时长、实际剪辑间隔和 1.2 倍速后的语音清晰度，必须如实说明。

### 第六步：一次最终检查与局部修复

按 `references/final-check.md` 完成一次整体终检。终检必须回看目标商品的原始讲解窗口，不能只检查已选片段。
发现错误时只修复受影响的商品归属、字幕、亮点、顺序或计算，不重跑无关步骤。只有输入变化、来源映射错误或质量条件失败时才重新打开整份方案。

## 4. 合规规则

### 全商品统一禁令｜两种更新入口
- **唯一权威执行库**：`references/global-rules.md`。所有现有及新增商品类目统一继承；专项模块不得覆盖、放宽或另外维护重复禁令。
- **更新入口仅有两种**：①用户提供抖音/千川违规审核截图；②用户明确说某词句违规或要求禁用。AI 识别截图实际指出的违规宣传，或按用户明确指定内容更新全局库。无法从截图可靠定位具体词句时才询问，不根据笼统“虚假宣传”“资质不符”推造禁词。
- **严格语义边界**：AI 识别字形、数字、口语和语义等价变体；相近但含量、成分、保证程度、对象或条件不同的表述不得自动扩禁。否定/引用语境需判断实际是否构成禁用宣传；用户明确要求“该词不论语境禁止出现”的按字面禁用。重复内容合并，记录截图或用户要求的来源；用户内部禁令不冒称平台通用禁令。
- **命中即排除完整原始字幕序号**：不能在同一序号中抠除违规词后保留剩余正常卖点。同一序号涉及其他商品也整条排除；跨连续序号共同构成禁用宣传时，仅排除确实参与构成该表达的序号，不连带排除其他正常序号；不扫描无关商品的全部窗口。
- **疑似识别错误**：能依据原始连续语境可靠确认命中时排除；无法确认时把相关序号标记待回听，暂不纳入正式成片，不得伪称已核实音频。
- **执行位置**：识别目标商品及其全部离散讲解窗口时同步筛查，在编排前排除确定命中的序号；从其他合规原话补足不同卖点并检查剩余语句完整性。原有一次最终检查对入选字幕、标题与话题核对；违规标题/话题仅重写受影响字段。命中时在例外中记录排除序号、对应禁用表述和原因；无命中不另出报告。
- **材质证明审核案例**：截图明确将某材质/成分宣传指认为需要证明且被拒审时，将能够定位的对应表述及其等价变体纳入全局禁令，命中即整条排除，即使后来拿到证明也不自动解除。不要仅凭一个材质名扩大到整类材质。纯商品资质/链接问题不自动转为禁词。
- **效率**：日常只用离线规则，不联网、不定期搜索、不建立新强制流程/程序/JSON。若用户另行明确要求调查官方政策，可单独处理，但不自动扩大全局禁用库。一般风险、动态价格/库存和未经证实的信息继续按 `references/qianchuan-offline.md` 及现有业务规则处理。
- **诚实与来源**：保留原始序号和原话；不改写、不跨商品混编、不声称平台保证过审；历史审核案例未直接证实的官方普遍禁词不得伪称官方规定。

## 5. 固定五部分交付

### 一、文件解析结果
写明文件名、输入类型、原始字幕条数/覆盖跨度（如可得）、执行模式（Standard/Long Context）、目标商品窗口数量、入选条数、组数、原始选段时长、预计 1.2 倍速成片时长，以及实际核验方式。若未运行程序，明确写“模型逐条对照，未运行程序”；不得写程序通过。末尾简要说明实际检查范围及合规风险。

### 二、商品识别
列出目标商品、别称、离散讲解窗口、必要的商品归属说明，以及加载的类目模块。多个商品未指定时，先询问，不进入正式方案。

### 三、最佳成片方案
默认一条；用户明确要求多条时最多三条。每版包括主题、侧重点、预计时长、原始选段时长、逐组原话与来源序号。
- 原话逐字保留，按成片播放顺序展示；不得润色或拼接造句。
- 每组使用简短作用标签，例如“开头钩子”“版型承接”“材质细节”“搭配补充”“自然收尾”。
- 逐版列出亮点覆盖清单，说明核心/次要、入选序号、同义关系和未入选原因；同一卖点保留两处时，标明第二处的强化价值，不把它误报为新的独立卖点。
- 仅将商品归属不明、明确已知不实、当前素材明确拒审、用户指定禁用句等真实例外单列；时长取舍与方案侧重点不是素材违规例外。
- 疑点紧邻对应片段说明，不得只在文末笼统提醒。
- 不显示逐句毫秒时间轴或冗长过程证明；SRT 仅给大致组级来源定位，逐条时长文本给未缩放累计位置估算。
- 30 秒及以下标记“短候选，非正式成片”。

### 四、作品标题与话题
每条方案恰好一个标题、**五个话题**。话题必须与当前商品、类目和该版主线相关；不得彼此重复。已加载的类目模块可以指定最多两个类目固定话题，通用核心生成其余话题补足五个；没有专项模块时，由通用核心生成五个相关话题。**通用核心不得强制加入其他类目的话题。**标题和话题不得编造事实、价格、库存或未证实功效；标题与主线一致。

### 五、原始 SRT 序号
按成片播放顺序列出原始序号。所有方案放在同一个文本代码框中，每版一行，半角逗号分隔、无空格，方案之间空一行；代码框内不放其他文字。不得伪造原始序号。

## 6. 能力与诚实边界

- 0.3.10 正式跨平台支持 SRT 和逐条时长文本。
- MP4、ASR、音画核验不在首版正式范围；没有实际视频能力时不得声称已看画面或听原声。
- 文件读取能力不足时，请用户粘贴文本或分段提供；不得声称完整读取未获得的内容。
- Python、计算器、脚本或其他工具都是可选增强，不是普通任务的必需条件；Long Context Mode 也不得把它们变成硬依赖。
- 不报告未执行的扫描、核验、测试或环境检查。

# Long Context Mode｜AI-First 长文本模式

## 目标

处理数百到数千条字幕、数十分钟到数小时直播文本时，降低截断、漏商品、漏离散窗口、前后归属污染和多方案漂移风险，同时保持 AI 为语义决策主体。

长文本模式不是“必须跑脚本模式”。它是一套 AI 分层阅读策略。

## 何时自动启用

不设置“超过N条就必须调用Python”的工具门槛。只要 AI 判断一次完整读取会显著增加以下任一风险，就自动启用：
- 宿主单次读取无法覆盖全文或已经出现截断；
- 字幕规模很大（约1000条以上是强信号，但不是硬阈值）；
- 时长达到数十分钟以上，特别是接近1–2小时；
- 多商品反复切换、同一商品多次回场；
- 关键词命中很多，但商品指代/别称复杂；
- 生成多条方案时，如果各自重扫全文会导致分析结果漂移。

2000条、接近2小时的素材应直接进入 Long Context Mode。

## Phase A：全局覆盖扫描（Coverage Scan）

目的只解决“有哪些商品、在哪些范围出现、什么时候切换”，不急着做最终卖点和成片。

AI 按可用读取范围依次覆盖全文，建立轻量窗口地图：

```text
商品A／别称
- 窗口1：序号 120–286
- 窗口2：序号 734–866
- 窗口3：序号 1510–1682

商品B／别称
- 窗口1：序号 310–522
```

规则：
- 分段之间保留必要重叠或边界上下文，避免商品切换发生在分割点时被漏掉。
- 关键词、查找或脚本只能帮助定位；“这个/它/刚刚那个/另一色”等指代和商品切换必须由 AI 判断。
- 价格、库存、互动、读弹幕和过渡话术可以标记为窗口属性，但第一轮不必深分析。
- 全局扫描完成后才能声称“已覆盖全文”。若某段未读到，必须明确缺口。

## Phase B：目标锁定与窗口合并

- 用户已指定商品：直接把全部同商品/别称窗口合并为目标窗口集合。
- 用户未指定且多商品明显：仍沿用现行规则，只询问一次目标商品；在等待选择时不做正式成片。
- 同一商品多次回场时，不能只取最长窗口、第一次窗口或关键词最多的窗口。全部离散窗口都必须进入下一阶段。
- 每个窗口按需要携带少量前后上下文，用于判断指代、回答弹幕、商品切换和款式边界；上下文只服务判断，不自动进入成片。

## Phase C：目标窗口精读（Deep Read）

只对目标商品全部窗口进行深读，识别：
- 核心卖点/购买理由；
- 次要卖点、颜色、搭配、使用场景、规格、尺码、适用条件；
- 顾客反馈与真实困扰；
- 同卖点不同表达；
- 动态促销/库存；
- 合规风险与事实待核项。

## Phase D：单一卖点池（Single Selling-Point Pool）

内部只保留轻量信息：
`卖点 | 来源序号/窗口 | 核心/次要 | 条件 | 同卖点第二处强化价值 | 风险/待核`

禁止恢复逐条字幕 JSON 台账。

卖点池规则：
- 先覆盖不同卖点。
- 同一卖点最多保留两处有强化价值的不同原话。
- 第二处必须至少增加一种价值：不同表达角度、补充条件/证据、顾客反馈、情绪强化、具体细节或更好的承接。
- 第三处及以上默认去重，除非其实是被误判为同义的不同卖点。

## Phase E：反向漏检（Reverse Coverage Check）

卖点池建立后，不直接出结果。AI 按窗口地图从头到尾回看每个目标窗口，逐窗口问：

> 这个窗口是否还有一个有购买价值、且卖点池里没有的不同信息？

重点检查：
- 后半段才出现的新卖点；
- 离散颜色/搭配/使用场景；
- 尺码与人群条件；
- 商品限制或安全条件；
- 顾客反馈；
- 第二处更强的同卖点表达；
- 其他商品事实是否误混进来。

反向漏检是 AI 语义复核，工具关键词扫描不能替代。

## Phase F：Single Analysis, Multi Output

用户需要1–3条方案时：
- 商品识别、窗口地图、卖点池、合规判断和反向漏检只做一次。
- 多方案从同一卖点池取材，保证来源与商品归属一致。
- 核心卖点允许跨方案重复；每条方案必须独立成立。
- 用不同开头、主线或次要亮点分配形成差异，不为了差异化故意删掉核心购买理由。
- 同一方案内部，同一卖点仍最多两处强化。
- 禁止“方案1重新扫全文、方案2再重新扫全文”的做法。

## Phase G：120秒价值装配

先建立高价值候选集，再计算1.2倍速预计时长。不要一开始为了短而过早删除卖点。

若超过120秒，按固定顺序删除：
1. 无关闲聊、动态促销、无购买价值互动；
2. 同卖点第二处强化；
3. 低优先级次要卖点；
4. 最后才动核心卖点。

目标是“120秒容器内装入最多有效购买信息”，不是必须填满120秒，也不是默认追求70秒。

## Phase H：终检与报告

最终检查必须确认：
- 全文扫描范围完整；
- 目标商品全部离散窗口已进入精读；
- 卖点池经过反向漏检；
- 多方案共用同一分析底座；
- 每版不超过120秒；
- 未实际执行的程序或音画核验没有被虚称。

文件解析结果中写明：`执行模式：Long Context`、全文覆盖范围、目标商品窗口数，以及实际使用的读取/计算方式。

## 工具降级

如果宿主有分段文件读取、精确范围提取或计算能力，可以使用；如果没有，则由 AI 按当前可读取文本分块执行同样流程。

**工具缺失本身不是失败。**只有文本无法取得、范围存在无法补齐的缺口或来源无法确认时，才说明受限。

# 通用开头、承接、结尾与原话规则

本文件适用于所有带货类目。若商品存在已建立的类目模块，同时读取该模块；类目模块只能补充本文件，不能覆盖全局原话、来源、合规和时长规则。

## 开头候选

- 开头候选必须与目标商品相关，原话完整、自然，脱离直播上下文后仍能理解，并能承接同一商品的后续内容。
- 候选包括：吸引人的外观/使用效果表达、商品核心卖点、真实顾客困扰、可信的购买者体验。它们没有固定机械排序；比较吸引力、相关性、具体程度、句子完整度和后续承接。
- 不要把“顾客困扰”标签直接当成排序结果，也不要把主播回答、主播个人偏好或一般选购建议伪装成顾客表达。
- 顾客自己提出的完整疑问或困扰可以作为候选；主播清楚转述顾客担忧时也可作为候选。主播回答应放在问题之后，不能单独冒充顾客问题。
- 顾客困扰必须表达顾客实际购买、使用或体验中的烦恼；商品属性本身、普通尺码建议、搭配建议、主播提问或泛泛描述不自动构成顾客痛点。
- 若主播明确确认目标商品确实存在顾客担心的负面表现，该困扰和确认性回答默认不入片、不作开头。用户明确要求围绕该问题制作答疑时例外，仍须忠实原话，不暗示商品能够解决它。
- 不得编造顾客问题、商品效果、用户评价或后续解释。没有合适开头时，选最清楚、最有辨识度的商品事实；仍没有则如实说明，不用促销、颜色词或碎片口播凑开头。

## 原话与语义

- 原话必须逐字保留；命中全局禁令时按完整原始字幕序号排除（不进行句内拆分）；其他非禁令的选段规则照旧，不得润色、改写、拼接造句或补充商品事实。
- 允许重排同一商品的原话，但必须保持对象、条件、因果和原意。不能跨商品拼接。
- “它/这个/那款”等指代不清时，先查必要前后文；仍不能确认商品归属则不入正式成片或明确标待核实。
- 连续原话整体可理解、只是疑似字幕识别错字时，优先原样保留并标记回听；不能仅凭错字擅自改写或拆句。
- 开头或片段若依赖“所以/但是/因为”等前文，补最短必要上下文或换更自然的候选；无法解决则不作为正式方案。
- 衔接困难不等于可以删除有价值的不同亮点。先寻找替代原话、调整顺序；仍需确认时保留并标“衔接需回听”。

## 中段与亮点顺序

- 开头之后优先接与开头问题或卖点直接相关的商品讲解，再安排其他核心理由和有用的次要理由。
- 一个商品主题通常先讲清楚，再切换到另一个主题；不要把无关细节插入顾客问题的直接回答之间。
- 搭配、颜色、使用场景、规格、尺码、维护方式和适用条件都可能构成购买理由，是否保留取决于商品类别、素材原话和购买价值。
- 不同事实不能仅因同属一个类别而合并。表达同一具体卖点时可以判为同义，但不要求一律只留一处：若第二处原话能提供不同表达、补充条件/证据、增强情绪或改善承接，且120秒时长允许，同一卖点最多保留两处；第三处及以上优先去重。
- 搭配建议中顺带提到另一件商品，不代表当前目标商品切换；只保留搭配关系和解释该搭配所必需的内容。另一件商品的独立规格不能混入当前商品方案。

## 结尾与动态信息

- 只有上下文确实表明是促成购买的自然话术，才作为结尾；避免强迫、虚假紧迫或无依据的稀缺表达。
- 价格、优惠、活动、赠品、实时库存、稀缺数量本身不等于商品亮点或逼单结尾。未经核实默认避开；用户要求保留且信息已核实时，放在商品讲解之后。
- 同一字幕同时包含商品信息与动态商业信息时，不擅自改写；按完整句边界处理，无法可靠拆分则整条暂不入正式方案并说明原因。
- 缺少真实促单结尾时，可以用商品亮点自然收尾，并如实说明素材没有合适逼单话术。

## 社会证明与事实

- 购买者真实反馈在来源清楚、原话完整且表达有吸引力时可以作为候选；裸销售数字、复购量或单纯“买了”不自动构成有力开头。
- 主播泛称“大家都喜欢”不等于真实顾客反馈。无法核实的社会证明要标记，不扩写为所有顾客都喜欢。
- 历史价格、库存、售后、链接、销量或活动不代表当前事实。不得将其写成当前承诺。
- 安全风险或明确不适用人群信息不能被悄悄删除或弱化；保留完整原话并标明需要核实的适用条件。若同条原始序号命中全局禁用表述，则全局禁令优先排除整个序号。

# 亮点盘点与选择规则（轻量版）

## 目的

完整找出目标商品所有有原话支持、商品归属明确的不同购买理由；在120秒上限内优先尽可能覆盖这些不同卖点和亮点。亮点盘点是语义工作，不需要逐条 JSON 台账或程序证明。

## 盘点方法

长文本任务先按 `long-context-mode.md` 建立单一卖点池；以下规则对 Standard Mode 与 Long Context Mode 同时适用。


1. 先确认目标商品的全部离散讲解窗口。
2. 通读每个目标窗口，识别不同购买理由，并保留对应原始序号。
3. 先拆分具体信息，再判断是否真正同义。同一品类、相似词或相似语境不等于同义。即使两句表达同一卖点，也不要求机械只留一处：若两处原话表达角度不同、第二处能补充证据/感受/条件或强化成交说服力，且时长允许，同一卖点最多可保留两处不同原话。
4. 对每个亮点标记核心或次要：
   - **核心**：直接影响商品是否适合、为何购买、关键功能/体验/适用条件的理由。
   - **次要**：补充搭配、颜色、场景、细节、规格或使用信息。
5. 商品归属不明时先查必要上下文；仍不明确的字幕不作为正式入选来源。
6. 只对真正存在疑点的内容做具体备注，不为每条字幕重复撰写语义总结或归属证明。

## 编排规则

- 默认单方案优先覆盖**全部不同核心购买理由**，然后尽可能纳入不同次要亮点；只要总时长仍在120秒以内，不应为了追求过度精简而主动删掉有购买价值的不同卖点。
- 多方案执行 **Single Analysis, Multi Output**：共用同一个商品窗口地图和卖点池；核心理由可重复使用，次要搭配、颜色和场景按各版侧重点分配，避免每版机械重复罗列。禁止每版重新全文扫描。
- 受120秒上限影响时，固定裁剪顺序为：无关闲聊/促销信息 → 同一卖点的第二处强化原话 → 低优先级次要亮点 → 核心卖点。也就是说，**先保不同卖点覆盖，再删重复强化**。核心亮点无法放入某版时必须说明具体取舍；有其他适合方案时优先安排到其他方案。
- 不因衔接困难、价值主观或内容较长而直接漏掉不同亮点；先找替代原话、调整顺序。仍有问题时标“衔接需回听”。
- 亮点覆盖清单按最终播放顺序展示，注明入选序号、核心/次要、同义关系和未入选原因；同一卖点保留两处时说明第二处为什么值得保留。
- 只有商品归属不明、明确已知不实、当前素材明确拒审、用户指定禁用句等真实例外才作为素材例外。时长取舍和方案侧重点不是素材违规例外。

## 最终反向检查

定稿前必须回到目标商品原始窗口，从头检查一次：
- 是否遗漏核心购买理由？
- 是否遗漏不同颜色关系、搭配避坑、规格条件、使用场景或限制？
- 是否把不同信息误判成同义？是否又把有强化价值的同卖点第二处原话过度精简掉？
- 是否有其他商品的规格混入？
- 是否有已选字幕其实不能可靠归属目标商品？
- 是否为了保留次要信息挤掉更重要的核心理由？
- 是否每个未入选的重要亮点都有真实、具体的安排原因？

程序、关键词搜索或已选片段复读都不能代替这次反向检查。不得声称程序证明亮点找全。

# 一次最终检查清单

每条正式交付在输出前完成一次整体检查。不要为此生成 JSON 台账或启动多轮程序工作流。

1. **输入完整**：确认实际读取的 SRT/逐条时长文本范围；有截断时补读，不能假称完整。Long Context Mode 必须确认全局覆盖扫描无缺口，并核对全部目标商品离散窗口已进入精读。
2. **商品归属**：每条入选原话确实属于目标商品；不同商品、不同款式的规格没有混用。
3. **类目规则**：已识别商品类别并加载已存在的适用模块；没有专项模块时没有借用其他类别规则。
4. **原话来源**：每条入选字幕原话、原始序号和来源位置一致；没有改写、补造或伪造编号。
5. **亮点完整性**：回看全部目标窗口，反向检查是否已在120秒内尽可能覆盖不同核心和次要亮点；同义判断必须准确。若同一卖点存在第二处有强化价值的不同原话，检查是否在时长允许时合理保留；每个卖点最多两处。
6. **结构与衔接**：开头自足且有吸引力；中段有相关承接；结尾自然；重排后对象、条件和原意仍正确。
7. **时长**：按1.2倍速计算，计入已知未加速内容；每版不超过120秒。接近上限需要删减时，先删无关内容和同卖点第二处强化，再删低优先级次要亮点，核心卖点最后动。
8. **合规**：检查目标商品全部讲解窗口、跨连续字幕的全局禁词及审核案例；明确命中即排除完整原始序号（同序号不拆句）。确认残余字幕仍语义完整；只把已确认命中列为违规，疑似错字待回听，未命中不额外报告。其他材质/功效/资质证据和动态信息仍按既有合规规则判断。
9. **标题与话题**：一个标题、五个与当前类目相关的话题；若专项模块定义类目固定话题则按模块加载并补足五个，未加载时不得强塞其他类目话题；遵守“羽绒服”标题/话题禁用规则。
10. **多方案一致性**：需要多方案时，确认它们来自同一个商品窗口地图与卖点池，而不是分别重扫全文造成归属或卖点漂移。
11. **AI-First 冲突检查**：确认本次没有把商品归属、卖点、重复、开头或合规判断交给机械工具；工具不可用时不会无故阻断任务。
12. **五部分输出**：顺序、来源序号代码框、方案行数和必要风险说明均正确。

# 女装与时尚配饰专项规则

适用范围：女装、常规服装、箱包及不属于鞋类/围巾配饰的时尚穿搭单品。鞋类统一由 `categories/shoes.md`、围巾/围脖/丝巾/披肩/围领配饰统一由 `categories/scarves.md` 专项处理；以这些商品为目标时不得叠加本文件的专项开头、选购及负面表达细则。通用规则、全局禁用词句、时长和输出要求以 `SKILL.md` 与 `references/` 为准；本文件不能覆盖它们。

# 开头钩子、商品顺序与句级处理

处理开头、材质平台反馈、穿搭搭配、逼单话术或商品归属前，先读本文件。这里是时尚品类的细则；通用判断仍遵循 `references/editorial-policy.md`。

## 开头：先识别候选，再比较吸引力

开头候选必须是目标顾客愿意听、原话完整自然、离开直播上下文也能理解的句子；它还要能接上同一商品的后续原话。候选包括有吸引力的外观表达、商品核心卖点和真实顾客困扰；这三类不是固定排序。先判断句子是谁在说、表达的是顾客的问题、主播评价、商品事实、穿搭建议，还是结尾话术，再比较吸引力、相关性、自然度和后续原话。不要把“困扰”这个标签直接当成排序结果。

按下面的规则筛选：

1. **外观表达可以是强候选。** 对服装、箱包等外观消费品，完整清楚的“穿起来很好看”“显瘦又好看”等表达可以开头；女性服装中“好看”是有吸引力的外观理由。多个外观句都自然、强度相近时，明确说“好看”的句子优先于普通外观夸赞。无需凭画面替原话背书；若没有看过视频，只把语气和实际穿着效果列为未核实项。孤立的“好看！”、“你们看这个”等碎句仍不够完整。
2. **商品核心卖点可以胜过弱开头。** 用原话里辨识度高、归属明确的核心卖点；例如羽绒填充标准或面料工艺可比身高/短款选购建议更适合作为开头。卖点是否适合开头，要与其他合格候选比较，不因它是材质/工艺就自动第一，也不因有顾客困扰就自动排在后面。若商品资料可用，核对标准、成分和工艺；没有资料时，仍可把原话作为剪辑候选，但必须在对应片段注明资料待核实。不要补写原话没有的标准、含量或效果；已知不实或明确被拒审的说法按例外处理。
3. **顾客困扰也是有条件的候选。** 只有素材明确呈现顾客使用、穿着或购买时自己的烦恼，或主播清楚地复述/转述了顾客的烦恼，才进入候选；结合共鸣强度、句子质量及后面有没有相关原话判断。困扰确实最能打动目标顾客且有相关后续时可以开头；用户明确要多条方案时，也可把合适的困扰放在另一条方案开头。若后续明确确认目标商品存在顾客担心的负面表现，该困扰和确认性回答默认都不进入成片，也不得作开头；用户明确要求制作这项答疑时，再按原话如实呈现，不暗示商品能够解决问题。没有明确确认负面表现时，清楚且有信息价值的顾客困扰仍可在后文保留，说明素材没有对应解释，不能暗示商品解决它。
4. **没有合适候选时，** 选素材中最清楚、最有辨识度的商品事实；没有就如实说明，不用颜色搭配、尺码建议、促销或碎片口播凑开头。

### 认定顾客困扰

- 顾客自己说出的疑问、担心或穿用问题可以算，包括弹幕中的完整问题；例如“顾客弹幕：小个子穿这件会不会显矮？”可保留完整问题本身作开头，后面接原素材中的衣长、腰线等相关版型介绍。主播回答放在开头钩子之后，作为后续内容；不能把回答句单独当成顾客困扰，也不能把“问题＋回答”整体冒充一条顾客困扰。
- 主播清楚概括“顾客担心……”“很多小个子担心……”时可作为候选；普通主播提问、主播自己的偏好或商品描述不能在没有语境依据时冒充顾客表达。“我喜欢这件”不能推成顾客喜欢；清楚表达“因为穿起来好看所以喜欢”的完整原话可按其实际意思评估。
- **顾客困扰说的是顾客会遇到什么，不是商品有什么问题。** “这种颜色比较怕流水印子”是在描述商品/颜色，不等于顾客担心；“浅色衣服容易脏，怕不好打理”若明确表达为顾客的使用烦恼，才可候选。尺寸、衣长、选长短款、选颜色、问如何搭配，通常是选购或搭配问题，不是开头痛点。
- 不按商品品类或困扰种类设置固定黑名单。只要原话或清楚的主播转述说明顾客购买、使用或穿着时会遇到的具体烦恼，就可作为困扰候选；再按共鸣、句子自然度和相关后续判断是否适合开头。显矮、怕冷、易脏不好打理、怕闷热、穿着沉、鞋磨脚、包不好用、围巾肤感不适等都按具体语境判断，不因为类别本身自动通过或淘汰。
- 商品本身的颜色、质量或商品属性描述，不会自动等于顾客困扰；必须说清它让顾客产生了什么实际购买或使用烦恼。尺码建议、选长短款和搭配/配色建议仍不作为顾客困扰开头。“好看”是女装有吸引力的外观表达；颜色搭配建议、“显白”或“显年轻”单独出现都不作开头。若完整句同时有明确的外观吸引力和搭配信息，按整句实际表达比较，不把颜色搭配误标成顾客痛点。

### 负面特点、劝退表达与安全限制

- **明确确认商品负面表现的困扰默认排除。** 当顾客提出某个穿着/使用负面表现，而主播明确确认商品确实有该表现（如问“肚子大了会显吗”，回答“有肚子一定会显”），整组内容默认不入片，不作为开头。只有用户明确要求围绕该问题制作答疑时才可使用，必须忠实原话且不补造解决办法。
- **中性特点与劝退表达分开处理。** 若中性特点和劝退话术属于不同字幕序号，保留有价值的中性特点，删除劝退话术。若两者在同一序号，不做句内拆分；结合商品、该特点对购买判断的重要性和是否有其他原话替代，决定整条保留或排除。
- 同一序号中的中性特点很重要，且找不到其他来源明确的原话表达时，优先保留完整序号，放在正文后段。不得为了凑亮点把劝退话术另行改写成文案。
- **安全风险或明确不适用人群优先完整保留原话。** 即使与其他商品描述同处一个序号，也不拆句；在相应位置标出需核实的安全/适用依据。若同条原始序号命中全局禁令，则整条序号排除，并在例外中说明。

### 句子完整、相关承接与方案差异

- 直接保留最完整、最能听懂的困扰句。只有“这个/它”等指代确实不清楚时，才把最短的必要前句一起放进开头；如果前文很长，找更短的困扰候选，或改用外观/核心卖点。
- 选定顾客痛点后，先接与该问题对应的商品讲解。例如显矮/显臃肿接衣长、腰线、版型；保暖担心接实际保暖讲解。对应主题完整讲完后再切换到材质或其他卖点；不要拿无关材质句替代版型回答。
- 不同开头候选都不强时，先换一段更短、更自然的原话，再考虑商品核心卖点。不要选读起来不通顺、需要猜错字、悬空的颜色词或“所以/但是”起头的半句。疑似转写错误保留原字并标回听，不代改。
- 只在用户要求的方案数内比较开头。默认一条；多条时分别寻找有吸引力且有后续承接的开头，并尽量错开中后段顺序。两条近乎重复或没有第二个合适开头时不硬凑。每版预计1.2倍速时长都必须不超过120秒。

## 商品描述、搭配、选购与结尾

- 通常先完整讲清一个商品主题，再切换到另一个主题。按素材和开头安排，可以先讲开头对应的版型/材质主题；版型、材质各自讲完再进入下一类。不得因“衔接不顺”删掉有用的不同亮点；先找原话、调整顺序，仍需确认的在相应组标“衔接需回听”。
- 完整盘点搭配、颜色和使用场景，并标注其购买价值。亮点清单保留素材中的不同信息；对单条方案，先纳入全部不同核心购买理由，再尽可能纳入有价值的次要搭配或场景。相同卖点不再机械只留一处：若第二处原话有不同表达、补充信息、情绪强化或更好的承接价值，且总时长允许，同一卖点最多保留两处。多方案可以共享重要理由，把次要的裤装、外套、颜色或场景分配给更匹配的方案，不要求每版重复罗列；次要亮点尽量安排在至少一版，确实受120秒上限影响时说明取舍。搭配建议里顺带出现另一件商品，不代表切换为介绍该商品；只保留搭配建议及直接解释该搭配的必要细节。另一件单品的独立规格不混入目标商品成片。
- 尺码与选购建议放在商品介绍之后。它们能帮助选择，但不因指向“小个子/高个子”就变成顾客烦恼或开头。
- 只有上下文确实表明是成片逼单/促成购买的话术，才把这段放在结尾。结尾保持自然。单独的价格、优惠、库存和稀缺数量不算结尾逼单，也不是必须覆盖的商品亮点；默认省略，除非用户要保留且当前信息已核实，此时放在商品讲解之后。若一个字幕序号里把赞美/商品信息与催单连在一起，整条序号统一放在结尾，不拆成开头与结尾，也不重复序号；其中的价格/库存要单独标记待确认，不能当作购买理由。发布前无法确认动态信息时，整条混合字幕不进入正式成片序号；在风险说明列出原序号和待核实项，不能只删其中一句。
- 购买者的真实反馈如“买过的姐妹都说好看”在来源清楚且表达有吸引力时可作开头候选；裸销售数字、复购量或单纯“买了”留在后段。明确无法核实的社会证明要标记，不扩写为所有顾客都喜欢。主播单说“大家都喜欢”不等于观众已表达喜欢。

## 用户指定禁用词句与审核截图

- 本类目和其他所有商品类别使用唯一全局禁用库 `references/global-rules.md`。截图或用户指定的禁令只在全局库维护，不在本类目复制禁词清单。
- 命中全局禁令时，直接排除**完整原始字幕序号**；即使同一序号包含其他正常卖点、其他商品，也不做句内拆分。连续多个序号共同构成禁用表达时仅排除实际参与的序号。
- 对截图能明确定位的材质证明拒审表述，按用户全局禁令排除；截图无法定位具体文案时再询问，不按材质词根扩大禁令。“羽绒服”仍仅禁止用于标题/话题，正文按全局规则。
- 除全局禁令外，普通事实缺证明/待核实等判断仍以通用合规基线为准；不以本类目规则放宽或覆盖全局禁令。

## 商品归属、事实冲突与话题

- 先认清主播正在介绍哪个商品。顺带出现的穿搭单品不是额外目标；明确切换后的其他款不混进当前成片。口播数字只有在语义明确指向款号或链接时才作商品标识；倒数、金额、尺码、销量或加库存后的报数不单独作为同款或链接证据，须结合明确的商品/链接话语和前后文。商品切换、别称和指代依据不够时查前后文，仍不清楚就标归属不明，不把它当成正式选段。
- 同品牌、同类的多个商品可以作为同一类目候选，但必须在工作判断和成片中区分款式/商品事实，不能把一件的版型、长短或面料说成另一件的。不同品牌、不同材质或明显不同款式应分别识别；不同长短款若同一设计/同款系列可放同一候选，但具体版型与衣长仍按各款归属标清。
- 商品资料与主播陈述冲突时，先用可靠商品资料确认；没有资料能判定时，优先保留说得更清楚且适合成片的一段，并在计划外说明原始矛盾。分别属于短/长款的衣长数字不是互相冲突。相反的主观穿搭意见可并存，保留各自条件，不伪装成同一事实。
- 标题和生成话题聚焦商品、外观吸引力或商品卖点，不以颜色搭配作为开头式话题，不写颜色名/配色组合；“显瘦又好看”这类原话有支持的外观利益可用。不得加入平台明确指出的违规词句、价格、库存、促销、SKU或未证实事实。本类目模块固定话题为 `#穿搭`、`#时尚营销`；通用核心再生成三个与该版商品/主线相关的话题，合计五个。该固定话题规则不得外溢到非时尚类目。
- **标题与话题全商品禁词：** 任何商品的作品标题和生成话题均不得出现“羽绒服”；仅该两个输出字段受此限制。正文原话、商品识别、素材例外和风险说明可以如实使用“羽绒服”，不因此删除正文。生成替代表达必须与原文支持的商品品类相符，不用猜测出来的词代替。

# 鞋类专项模块（Shoes）

## 适用范围、路由与边界

适用于所有作为目标商品销售的鞋类：单鞋、高跟鞋、平底鞋、皮鞋、靴子、雪地靴、运动鞋、跑鞋、休闲鞋、凉鞋、拖鞋及其他鞋型，不限性别与季节。用户指定商品优先；顺带提到的裤子、袜子、包或其他鞋款只是搭配/对比，不自动切换目标。与 `categories/womens-fashion.md` 采用排他式品类路由：以鞋类为目标商品时加载本模块，不同时加载女装模块的开头、排序、适配等专项规则。

必须服从 `SKILL.md`、`references/editorial-policy.md`、`references/highlight-selection.md`、`references/global-rules.md` 与 `references/qianchuan-offline.md`。本模块只增加鞋类语义判断，不新增固定输出、时长、工具或环境条件。以下范例仅用于解释判定，不能当成实际素材原话。

## 1. 开头：按鞋款动态判断

- 在原话中比较整体外观、上脚效果、鞋型、脚感、工艺/功能、真实顾客困扰等候选；以吸引力、商品相关性、语义完整度、后续承接与可信度决定，不设置“好看/舒适/痛点”机械排名。
- 顾客困扰须真实来自顾客原话或主播明确转述；普通尺码咨询、搭配建议、主播自问自答不能冒充顾客困扰。
- 开头依赖后续真实原话支撑，不能把“防滑设计”扩成“任何路面都不打滑”，不能把个体穿着感受扩成普遍保证。动态价格/库存不作默认开头。

## 2. 卖点盘点与中段装配

- AI 对实际字幕逐一识别：外观与上脚效果、鞋头/鞋型、修饰效果、鞋面及内里、鞋底结构、软硬与回弹感、重量、跟高、鞋筒/筒围、脚型与尺码适配、材质工艺、搭配、配色、使用条件及场景。以上是候选清单，不要求每款鞋都有。
- 分清独立购买理由：鞋底柔软、前掌空间、鞋跟高度、裤装搭配各有不同决策意义；不能笼统合并为“舒服/百搭”。单独的不同颜色、服装名称也不自动算新的购买理由，须判断真实信息增量。
- 核心卖点完整优先。紧接开头讲清对应核心主题，再安排其他核心理由，最后结合信息增量安排次要搭配、颜色及场景。按语义与原话自然衔接动态排序，不固定“鞋型→材质→脚感”。
- 同一卖点最多保留两处原话，第二处须有新信息、补充条件、独特体验或有效情绪强化；不同购买理由分别计数。累计时长及压缩顺序完全沿用通用核心的 1.2 倍速、120 秒上限。

## 3. 脚型、尺码、穿着适配

- 分别识别脚宽、脚背高低、鞋头空间、脚长/尺码、鞋筒与腿围、鞋跟高度、试穿脚感、走路适应条件。哪些是核心取决于实际鞋款及字幕购买价值，而非固定全部置后或全部优先。
- “建议大一码”“脚背高不适合”“此款偏窄”等如来自可靠原话，应保留所依赖条件；不自行推断所有宽脚、胖脚、长时间步行均适配。买鞋建议不能被改造成承诺。
- 有明示的不适用条件、安全限制或相反证据时，不得通过截去条件留下“人人适合”“完全不会磨脚”等误导性正面承诺；无法同时在成片中可靠表达必要条件时，排除相关可能误导的正面原话并说明。

## 4. 材质、设计、体验、性能、风险

- AI 区分 **材质/参数事实**（如真皮、跟高厘米数）、**结构设计**（如防滑纹路）、**主播主观体验**（如踩着柔软）、**客观功能主张**（如防水、防滑）与**绝对化承诺**（如永不磨脚、走一天都不累）。不同类型不能互相证明。
- 对未有商品资料佐证的材质、功能与使用效果，按通用合规规则标待核实，不因缺少证明就一刀切删除全部材质原话；已知不实、已明确拒审或命中全局禁令时按更高优先级规则处理；明确命中全局禁令的，排除完整原始字幕序号，不在本类目句内拆分。
- 不凭鞋型或材质自行推出防滑、防水、耐磨、矫正姿态、治疗足部不适等效果；涉及医疗/健康效果须核实依据与平台限制，不把设计特征当实测性能。
- 普通负面体验（如新鞋略磨脚）按通用负面表述规则取舍；重要脚型限制、安全提醒不可被剪掉后使保留原话失真。对应正面与限制互相矛盾时先核对商品归属及上下文，仍不明则不作无条件承诺。

## 5. 多颜色、多版本与跨商品归属

- 同一商品不同颜色可以共用确实适用于各色的描述；颜色专属鞋面、材质、搭配及外观只归对应颜色。
- 不同鞋型、鞋底结构、跟高、靴筒、尺码版型、材质及明确不同链接/款号，按实际证据分别判定；同系列不自动等于同款，不同颜色也不自动等于不同商品。
- 不跨款继承脚感、功能、尺寸、鞋跟和适配建议；归属不确定则按通用核心核对上下文，仍不明时不选入正式成片。

## 6. 搭配、场景与画面依赖

- 分开盘点鞋与裙子、牛仔裤、西裤等搭配关系、颜色关系、整体穿搭效果及通勤、运动、休闲、约会等实际场景；按真实信息增量和时长动态取舍。主播提到某场景不等于证明鞋适合长时间负荷使用。
- “你看这个鞋头”“我这样弯给你看”等需画面才能判断的原话，若语义完整、有购买价值可列为候选并就地标注“画面待核实”；完全依靠画面、脱离视频无明确语义的空泛话语默认不入片。仅有 SRT 时不得声称看过上脚画面或演示。
- 自然结尾与动态价格、促销、库存、社会证明均执行通用核心；不创作原字幕没有的逼单句。标题与话题延续时尚类目原有固定 `#穿搭`、`#时尚营销`，其余由核心补足五个并严格遵守全局标题禁词。

## 反向检查（无需额外工具）

定稿前问：是否错把脚感、鞋底、跟高、脚型适配当同义；是否跨颜色/跨鞋款混用事实；是否漏掉关键使用限制；是否把未经核实功能夸成保证；画面依赖是否标注；不同搭配是否有增量；每一处原话、字幕序号及条件是否可回查。失败只修复相关字幕组，不重跑整份工作流。

# 围巾与颈部穿搭配饰专项模块（Scarves）

## 适用范围、路由与边界

适用于以围巾/颈部穿搭配饰为目标商品销售的针织围巾、羊毛/羊绒围巾、皮草/毛绒围脖、丝巾、披肩、围领等，不限季节；按照实际商品属性识别，不把丝巾一律当保暖用品，也不把冬季围脖一律当纯装饰品。披肩属于本模块的前提是它作为围巾/披肩类配饰销售；如果销售对象实际是外套或其他服装，按商品事实路由。以围巾为目标时不并行套用 `categories/womens-fashion.md` 的专项开头和适配规则。

必须服从 `SKILL.md`、`references/editorial-policy.md`、`references/highlight-selection.md`、`references/global-rules.md` 和 `references/qianchuan-offline.md`。本模块不改变原话、序号、时长、五部分输出及日常 AI-First 主路径。例句只解释规则，不得生成虚构原话。

## 1. 开头：按产品及原话动态选

- 比较外观、毛感/光泽/质感、佩戴效果、肤感与保暖、穿搭价值、真实顾客困扰；按吸引力、可信度、语义完整性、商品归属及后续承接动态决定，没有“材质优先”“好看优先”或“痛点优先”的死顺序。
- 一般颜色搭配建议不自动升级为强开头；只有完整原话确有明确穿搭利益、且后续相关讲解可承接时才参与比较。
- 顾客困扰须是真实顾客表达或主播明确转述；不得把主播对商品的评价冒充顾客烦恼。价格/库存不作默认开头。

## 2. 中段：不同购买理由与重复强化

- 完整盘点有原话支持的不同亮点：外观/佩戴整体效果、毛感蓬松度、光泽、材质成分、厚薄/重量、柔软肤感、保暖体验、尺寸长短、垂坠感、图案花色、围法、层次感、用途变化、与服装及颜色的搭配、使用场景、护理及适用条件。
- 核心卖点完整讲清后，再尽量覆盖有信息增量的次要卖点；根据开头及原话承接动态排列，不机械按“材质→保暖→搭配”排序。不同毛感、佩戴层次感、柔软肤感、具体系法不应被笼统合并为“好看”。
- 同一卖点最多保留两处确有补充/强化价值的不同原话；相似描述无新信息的不为凑时长重复。时长上限、取舍顺序严格继承 1.2 倍速不超过 120 秒的核心规则。

## 3. 材质、质感、肤感、保暖与依据

- AI 区分 **材质/成分事实**、**可描述的视觉质感**、**主播主观肤感**、**保暖体验/客观性能**、**绝对化承诺**。材质名称不能推出含量、品质、保暖等级、一定不扎皮肤或适合敏感人群；主观体验不推出所有人有同样体验。
- 兔毛、羊绒、羊毛、皮草、龙猫毛等称谓按原话识别并注意是否只是商品俗称；不能仅凭名称确定真实材质/动物来源/含量。缺材料证明时标明待核实，已知不实/明确命中全局禁令按通用规则处置；禁令命中时排除完整原始字幕序号，不扩大到无关序号。
- “绝不掉毛”“所有人都不扎”“任何气温都保暖”等高风险泛化说法须结合语境及证据处理，不因为原话存在就认定功效真实。

## 4. 围法、佩戴效果与画面

- 不同围法、绕圈/套头/披肩/系发等如确实不同、且主播原话给出具体佩戴利益，可分别作为购买理由或有价值的补充；不要因为都属于“佩戴”就机械去重，也不因动作不同就机械认定信息增量。
- “这样一弄”“你们看这里”等只有画面才能解码的碎句，默认不入片；有完整信息的佩戴讲解即便依赖演示，可作候选并就地标记“佩戴画面待核实”，不能从字幕凭空补出系法细节。
- 使用方式是否实际可行、画面是否对应、成片剪点是否完整，只有视频或可靠商品依据才能进一步确认；纯 SRT 不声称已验证。

## 5. 搭配、配色与使用场景

- 分开识别与大衣、毛衣、羽绒外套等服装的搭配、明确颜色关系、穿搭效果、季节/出行场景；保留有信息增量的不同理由，在核心价值与 120 秒限制下动态取舍。
- 不同服装名称并不必然意味着不同卖点；“所有衣服都百搭”不能凭空证明每一种搭配。顺带提到服装时不把该服装规格和独立卖点串入围巾文案。

## 6. 商品归属、版本与护理限制

- 同款不同颜色可以共享通用事实，但毛质/材质、尺寸长短、双面设计、独有图案、围法及穿戴效果必须分配到正确颜色/规格/款式。不同材质、不同链接或明确不同围脖不可因同类或同系列直接混作一件。
- 区分普通负面体验（如浮毛）、重要肤感/敏感人群限制、护理要求（如干洗）、安全/使用注意事项。普通信息按购买价值取舍；重要限制不得被删除后留下“所有人适合”“完全不扎”等误导性结论。条件无法可靠表达时同步排除可能误导的正面承诺。
- 不由 AI 凭材质推断一定掉毛、需要干洗、敏感皮肤一定能戴；以原话及商品资料为据，事实有疑点就地标待核实。

## 7. 多色/多条购买建议与促单分开判断

- “建议买两条”“多备几个颜色”本身是促单，不自动成为新的商品卖点。若原话确实说明一条搭大衣、一条作日常佩戴等不同使用/搭配价值，识别这些**独立理由**，再按时长和购买价值决定保留。
- 与其他围巾/竞品的价格比较、到手价、折扣、库存与稀缺，均按通用动态信息合规规则核实；未经核实不作为现时事实或强制收尾。不同商品的价格不能被误认为目标商品价格。
- 自然结尾优先使用原字幕中真实完整的推荐/促单原话，不强塞单纯报价格、数量或未经核实的比较价。含动态信息与其他内容的一条字幕，按通用整句/整条处理边界，不擅自删掉其中几个字绕过核实。
- 标题和话题延续时尚类目原有固定 `#穿搭`、`#时尚营销`，由核心补充到五个；服从全局禁词、标题不得编造信息。

## 反向检查（无需额外工具）

核对是否误把质感、肤感、围法、佩戴效果、配色、搭配与场景合并；是否误把两条购买建议当两个卖点；是否将兔毛、龙猫毛等不同商品的材质与价格串用；是否漏掉重要适用/护理限制；视觉依赖与材质依据是否准确标注。只进行一次终检和必要局部修复。

# C2 Universal｜固定版本更新协议 (Update Protocol)

> 治理级规则。适用于今后每次业务规则、类目模块、平台适配、长文本、性能、合规基线及发布流程的变更。执行优先级：AI-First Constitution > 本更新协议 > 具体业务模块。不得以本协议替代或降低 SKILL.md 的现有剪辑要求。

## 一、更新的六项固定审查

1. **AI 主导**：先写出不依赖 Python、脚本、API、联网或中间 JSON，且原始文本可靠可读时 AI 能独立执行的主路径。商品归属、亮点、语义去重、结构、合规语境与最终取舍仍归 AI。
2. **工具最小化**：新增工具须明确机械用途、触发条件、准确性或端到端效率的可验证收益。禁止将工具可用性、环境自检或多层 Gate 设为普通文本任务前置条件；不得为实现形式上的自动化而增加重复调用。
3. **环境零强制与自动降级**：说明工具不可用时的 AI 主路径、需要告知用户的核验边界，以及仅在输入本身缺失、不可恢复的截断、关键来源无法确认等情况下暂停受影响部分；不能伪称运行过程序。
4. **质量不退步**：逐项核对原话真实性、字幕编号与来源、商品归属、不同核心/次要亮点与反向漏检、合规语境、1.2 倍速 120 秒硬上限和固定五部分输出。不得以减少步骤为理由牺牲这些条件。
5. **更新验收**：对受影响路径做最小充分回归；覆盖常规文本、相关长文本/多商品/多方案和对应类目场景。开发期可按需使用测试脚本；不得让发行测试成为日常执行的硬依赖。未实际测试的项目标记“未验证”。
6. **发布与同步**：记录实际变更的文件、版本号、GitHub/插件/便携包/云盘各渠道状态；仅对实际上传且可核实的渠道声明“已同步”。对比端到端耗时与工具调用次数时，只能报告实测，不得凭推测断言“更快”。

## 二、三条一票否决

- **无明确收益的工具否决**：新增日常工具调用，却无法说明其明确、可核实的准确性或端到端效率收益，不得发布。
- **质量下降否决**：简化步骤导致原话被改、商品串用、不同关键卖点漏选、来源编号错误、时长计算不可靠或合规误判，不得发布。
- **新环境硬依赖否决**：本来 AI 可以仅凭可靠文本完成的普通任务，新版本要求先装 Python、安装依赖、联网、生成 JSON 中间件或通过环境测试才能开始，不得发布。

上述条款不得用于禁止必要的可选机械校验：复杂长文本或时长计算可按需调用工具；其结果不能替 AI 作语义决策。

## 三、每次更新的固定记录格式

- **基准与目标版本**：旧版本 → 新版本；改动性质（业务/类目/平台/效率/治理/修复）。
- **变更范围**：具体文件、变更理由、影响场景和明确不变的规则。
- **AI 独立主路径**：在可靠文本可读且无工具时如何完成核心任务。
- **工具决策与降级**：每项工具的用途、触发条件、增益证据、不可用处理。
- **质量与兼容检查**：原话、商品归属、卖点覆盖、时长、固定五部分及相关类目/长文本检查结果。
- **端到端效率**：实测数据和条件；没测则写“未测”，不得以减少步骤数冒充耗时提升。
- **发布状态**：GitHub / 私人插件 / 便携包 / 云盘 / 其他平台逐项写“已核实 / 未同步 / 待核实”，不得笼统宣称全部完成。
- **最终判定**：“通过 / 不通过 / 待验证”，三项一票否决逐项写明。

## 四、执行边界

本协议只约束未来版本的**开发与发布**，不增加每次使用“srt文案”时的分析步骤、固定表单、Python 调用、环境检查或额外对用户展示的字段；日常五部分交付保持不变。

版本升级完成后，只有通过核验的已发布渠道才可称为“当前已更新版本”；其他渠道必须明确保留旧版状态。
